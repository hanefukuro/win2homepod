# 実機検証 2026-10-18

同じLANのHomePod 2台で、PR #6の実験CLIとPR #4の左右テストを検証しました。
機器名、IP、機器ID、ユーザーパス、鍵はこの記録に含めません。
結果はこの2台・この時点の実装に限り、他機種・OS版への一般化は行いません。

追加のWASAPI取得・5分連続送信・マイク予備測定は[REAL_DEVICE_SOAK.md](REAL_DEVICE_SOAK.md)に記録しています。
40 msの合成左右テストで鳴った結果とは別に、40 msのWASAPI経路は無音との聴取回答とマイク一致なしでした。
150 msのWASAPI経路では5分の送信と聴取確認ができ、送信前音からマイクまでの予備値は約440 msでした。
ドライバーの固定遅延を校正していないため、この値は厳密なゲーム操作からの総遅延とは扱いません。

## SETUP probe（PR #6）

対象コミット: `e1df366db0a6f380a200fddb938a6a8893fd9365`。
type=96、44.1 kHz、audioMode=defaultを共通とし、下記だけを変更しました。
待ち時間は指定がない行ではlatencyMin=latencyMax=6615 frames（150 ms）、spf=352です。

| 宣言 | 2台のstream SETUP | arrivalToRenderLatencyMs（両方） |
| --- | --- | --- |
| ALAC / ct=2 / audioFormat=0x40000 / PTP | 200 | 69 |
| PCM / ct=1 / audioFormat=0x800 / NTP | 200 | 70 |
| PCM / ct=1 / audioFormat=0x800 / PTP | 200 | 69 |
| ALAC / PTP / 待ち時間40、50、60、70、80 ms | 全設定200 | 全設定69 |
| ALAC / PTP / spf=176 | 400 | 取得なし |
| ALAC / PTP / spf=88 | 400 | 取得なし |

計20回のprobeで、16回はstream SETUPまで成功し、4回はstream SETUPで400でした。
全20回のTEARDOWN応答が200、音声送信パケット数は0でした。
成功ケースではtransient pair-setup、session SETUP、RECORD、PTP時のSETPEERS、stream SETUPまで確認しています。

この比較では、PCMへの変更や小さい待ち時間の要求によって申告値が下がる結果は得られませんでした。
`arrivalToRenderLatencyMs`は受信機が返したフィールドと値であり、外部測定した総遅延ではありません。
69/70の差から優劣を判断せず、70 msが全経路の固定下限とも結論しません。
spf=176/88の拒否も、今回の宣言の組合せに限った結果です。

再現にはLOW_LATENCY_PATHS.mdのprobeを使い、設定ごとに別の出力ファイルを指定します。
40、50、60、70、80 msのlatencyMin/Maxは、それぞれ1764、2205、2646、3087、3528 sample framesです。

## 左右テスト（PR #4）

対象コミット: `da16418f0c1bb9a4f0ae07e8c63cacfbf9b4e1ae`。
PRのソースを一時フォルダーへ展開し、実際のMainFormのStartAudio(true)を検証ハーネスから呼び出しました。
テスト専用の設定・ログを使い、通常のアプリ配置と設定は変更していません。
VB-CABLEへの切替を無効にし、合成した左右テスト音だけを2台へ送信しました。

最初の150 ms / -30 dBの12秒テストは、パケット送信と自動停止が正常でも、聴取者から「聞こえない」との回答でした。
150 msのまま音量を普段の保存値-18 dBに変更した再試験では、聴取者が左右の出音を確認しました。
この比較だけで初回の無音原因を音量と断定はしません。

150 ms / -18 dBでは、2台の送信数が1506 / 1551パケット、送信エラー・再送要求は両方0でした。
診断欄の要求150 ms・総遅延未計測の表示、12秒後の自動停止、全Windows出力ロールの不変、復元記録が残らないことを確認しました。

続けて同じ-18 dBで80 → 60 → 40 msを各12秒実行し、聴取者が3回とも左右の正常な出音を確認しました。

| 要求待ち時間 | 受信機1 / 2の送信パケット数 | 送信エラー / 再送要求 | 左右の出音 |
| --- | --- | --- | --- |
| 150 ms | 1506 / 1551 | 両方0 / 0 | 聴取確認あり |
| 80 ms | 1508 / 1549 | 両方0 / 0 | 聴取確認あり |
| 60 ms | 1507 / 1543 | 両方0 / 0 | 聴取確認あり |
| 40 ms | 1506 / 1554 | 両方0 / 0 | 聴取確認あり |

4設定とも、要求値と総遅延未計測の診断表示、自動停止、全Windows出力ロールの不変、復元記録が残らないことを確認しました。
受信機のarrivalToRenderLatencyMsは全設定69でした。
40 ms設定で正常に鳴ることは、総遅延が40 msであることを意味しません。
50 / 70 msはSETUP probeだけを行い、音声送信は行っていません。

## 残る検証

- PCM宣言に対応したencoder・packetization・syncと実際の音声送信。
- 外部の音響測定による総遅延と複数台の同期誤差。
- 長時間再生、通常のWASAPI取得、ネットワーク変動、音切れの定量評価。
- Apple senderの実トラフィックに基づく他のtype/mode/codecの比較。

短い左右テストやSETUP 200だけを、ゲーム用途の遅延や長時間安定性の合格とは扱いません。
