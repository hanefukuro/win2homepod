# Win2HomePod

Windowsの再生音を、同じLAN上のHomePodへAirPlay 2で送るWindowsアプリです。
受信機はmDNSで検出し、利用する機器を画面で選択します。

## 必要なもの

- Windows 11
- ビルド: .NET 10 SDK
- 実行: .NET 10 Desktop Runtime
- 同じLANに接続した対応HomePod
- 任意: [VB-CABLE](https://vb-audio.com/Cable/)（専用の仮想音声出力を使う場合）

音響補正ソフトや特定のPC構成は必要ありません。
VB-CABLEは別ライセンスのDonationwareで、インストーラーは同梱しません。
VB-CABLEがない場合は、Windowsの現在の既定出力を取得します。PC側からも音が再生されます。

## ビルドと起動

PowerShellで以下を実行します。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1
```

ビルドした `app/` フォルダー全体を、`Start.cmd`・`Stop.cmd` と同じフォルダーに配置します。
`Start.cmd` で起動し、`Stop.cmd` または画面・トレイの終了操作で終了します。

1. 初回起動で、検出された受信機から使うものを選択します。初回は自動送信しません。
2. 再生待ち時間・音量と、VB-CABLEへの出力切替の有無を選び、「音声を送信」を押します。
3. 次回起動時は保存した接続先へ自動接続します。保存先が見つからない場合は自動接続を保留します。
4. 最小化するとトレイに常駐します。閉じると送信を停止して、切り替えたWindows出力を元へ戻します。

接続先・待ち時間・音量は、このアプリの配置先にある `.state/settings.json` へ保存します。
別のPCにコピーする場合は `.state/` を含めず、そのPCで設定してください。
ログイン時の自動起動やデスクトップショートカットの登録は行いません。
操作画面だけを開くには `app/Win2HomePod.exe --no-connect` を使います。

## 音声経路

通常は現在の既定出力をWASAPIループバックで取得します。
VB-CABLEをインストールすると、画面で専用出力への切替を有効にできます。
その場合は、Windowsアプリ → VB-CABLE → WASAPI取得 → 44.1 kHz / 16 bitステレオALAC → HomePodの経路になります。
仮想出力は標準の `CABLE Input (...)` の名前で検出します。Windowsの既定の通信出力は変更しません。
アプリ単位で出力を指定している場合は、そのアプリの出力設定も確認してください。

複数の受信機には共通の音声ソースとPTP時計を使います。
ステレオペアはHomeアプリ側で設定してください。Win2HomePodはペア構成を変更しません。
Windowsの音量とミュートは、VB-CABLE経路の送信音声にも反映します。
他の音声ソフトを停止したり、その設定を変更したりする機能はありません。

## 再生待ち時間

100 / 150 / 200 / 250 / 350 / 500 / 1000 / 2000 msから選択できます。初期値は150 msです。
250 ms未満は実験設定です。音切れする場合は500 / 1000 / 2000 msへ増やして再送信してください。
この値はAirPlayの設定値で、実測した総遅延ではありません。
Windowsのバッファ、ネットワーク、受信機処理も総遅延に加わります。
WASAPI取得は20 msを目標とし、キューが80 msを超えると40 msまで追従して累積遅延を抑えます。

## クラウドCI

GitHub Actionsで、PR・mainへのpush・`codex/**`へのpush・手動実行時に検証します。
LinuxとWindowsで機器不要のプロトコル・設定テストを実行し、WindowsでReleaseビルドと
`--render` による画面生成のスモークテストを行います。実機の探索・送信は行いません。
成功したrunのArtifactsから `Win2HomePod-win-x64` をダウンロードし、展開して使えます。
実行には.NET 10 Desktop Runtimeが必要です。テスト結果と画面画像も別Artifactとして保存します。

CIはHomePodの出音、実測総遅延、WASAPIの取得周期、ネットワーク変動下の安定性を検証しません。
低遅延経路の調査（#2）と現行経路の最適化（#1）は、CIで機器不要部分を検証し、実機測定を別途行います。

## 検出できない場合

通常はmDNSを使うため、IPアドレスの事前設定は不要です。
マルチキャスト受信が制限されている場合は、任意で直接DNS-SD問い合わせを併用できます。

1. `receiver-hints.example.json` を `.state/receiver-hints.json` にコピーします。`.state/` がなければ作成します。
2. 空配列を、そのLANで使う受信機のIPv4アドレスを列挙したJSON配列に変更します。
3. アプリを起動し直します。接続先は問い合わせの応答から検出します。

実際のIPや機器名を含むヒントファイルはGit管理対象外です。
ファイアウォールの確認が出た場合は、使用するプライベートネットワークで許可してください。

## 復元と制限

- 停止時は元のWindows出力へ戻します。送信中に手動で別の出力を選んだ場合は、その選択を尊重します。
- 強制終了時は次回起動でWindows出力の復元を試みます。アプリの配置先は移動しないでください。
- 複数台への接続中に片方が失敗した場合、すべての接続を停止します。
- 自動再接続はありません。ネットワーク断では停止して再送信してください。
- 別の音声ソフトがWindowsの既定出力を自動で変更すると、仮想出力への音が途切れる場合があります。そのソフト側の自動切替を無効にするか、終了してから送信してください。
- PTPはUDP 319/320を使います。他のAirPlay送信アプリとの同時使用は避けてください。
- 仮想音声ドライバーは終了後もWindowsに残ります。
- 長時間安定性・実測遅延・複数台の音響的な同期精度は保証しません。

## ローカルデータと共有時の注意

`.state/` はすべてGit管理対象外です。ログ・設定には受信機名、IP、機器ID、音声出力ID、利用時刻などが含まれます。
問い合わせや共有の際も、そのまま添付せず内容を確認してください。
音声・マイク・動画の録音機能はありません。

- `.state/app.log`: 接続・入力レベル・パケット数・再送・エラー・取得キューなど。日付変更または10 MBで別名へ退避します。
- `.state/settings.json`: 選択した機器ID、音量、待ち時間、出力切替の設定。
- `.state/output-recovery.json`: Windows出力の復元記録。復元後に自動削除します。
- `.state/receiver-hints.json`: 任意の検出用IPヒント。

ログフォルダーはトレイのメニューから開けます。
ソースを共有する場合は `.state/`、`.tmp/`、`app/`、`bin/`、`obj/`、アーカイブや秘密情報を含めないでください。

## 別の低遅延経路を調べる（Issue #2）

実験用CLIでcapabilityを保存し、stream type・codec値・audio format・spf・timing等を変えたSETUPを試せます。
音声は送信せず、accept/rejectの記録後にTEARDOWNします。既存GUIの送信経路は変更しません。
`./build-probe.ps1`で`probe-app/`へビルドします。クラウドCIもこのCLIをビルド・テストします。
操作方法、比較元の実装、実機で確認する項目は[調査メモ](docs/LOW_LATENCY_PATHS.md)に記載しています。
